## Verdict

**Not yet.** OpenTabletop has now closed the ordinary map-drag defect, the scoped plugin confidentiality defects, and the observed onboarding omissions. Native image placement, fractional calibration, authenticated player preview, portable recovery, and SDK packaging have concrete outcome evidence. The remaining blockers are materially different: the packaged desktop executable fails clean startup, loaded responsiveness missed the proposed target, known production dependency repairs remain unapplied, native prepared-map import is absent, and a third party still cannot deliver playable rules through the public system path. These prevent the full better-than-Roll20 and demonstrated long-term-threat verdict; repaired findings are not being held open to preserve that conclusion.

This is the user's full product objective. Self-hosting alone, a large feature inventory, and green regression tests are insufficient substitutes. Conversely, the bar does not require copying every licensed book, matching every community sheet, or proving how a competitor's employees would react. A credible advantage can coexist with Roll20's larger content ecosystem if complete preparation, play, recovery, and extension workflows give users compelling reasons to switch.

The comparison remains against the [current official-source Roll20 baseline](roll20-baseline-2026-09-05.md), accessed September 5. That baseline includes native UVTT import, guided grid alignment, true Player View, connected character/content workflows, and established hosted distribution. It is documentation evidence, not a newly timed hands-on Roll20 session. No speed ratio, time-saving estimate, or user-preference result is established here.

[Official Electron module documentation](https://www.electronjs.org/docs/latest/tutorial/esm#sandboxed-preload-scripts-cant-use-esm-imports).

Build the repaired artifact, start with fresh owned user data and no supplied secret, verify the desktop renderer API, bootstrap/import/resume with a separate player's correct permissions, close/restart, and confirm durable state and stable signing. ### P2 — A third party cannot deliver a playable rules system through the public system path

External system registration rejects capabilities beyond `data-model` (`apps/api/src/app.ts:12503–12505`); executable capabilities are granted to bundled IDs in `apps/api/src/registries.ts:95`. Sheet and quick-roll dispatch compare those IDs directly (`apps/api/src/app.ts:26738–26761`), with similar bundled dispatch for actions, rest, advancement, and compendiums. Generic Fantasy, Stellar Frontiers, and Mystic Noir therefore establish bundled breadth, not an outside author's executable extension path.

The example's manifest declares only `data-model`, while its source declares runtime capabilities. SDK registration arrays have no discovered host consumer, ordinary plugin discovery requires `plugin.manifest.json`, and directly registering the example's ID conflicts with the bundled system. External actor/item schema paths are persisted without their schemas being loaded and enforced (`apps/api/src/app.ts:12515–12518`, actor creation remains D&D-specialised). The registry UI also calls every entry bundled/loadable and claims starter/SRD compendium entries despite the API exposing actual source/capability distinctions (`apps/web/src/sdk-panel.tsx:344–351`). The documentation's candid `data-model` limitation does not close the larger promised workflow.

**Smallest useful implementation:** support one constrained declarative external-system package, not unrestricted arbitrary code. Load and validate its versioned local actor/item schemas; consume a bounded sheet/quick-roll/action definition through a registry adapter and the existing dice engine; permit resource changes only through existing typed domain commands with caller checks. Advertise only capabilities the adapter actually implements. Use the registry entry to dispatch this path instead of adding another hardcoded system-ID switch. Correct the example and UI labels to match the supported path. Further capabilities need not be advertised merely to match the bundled manifests.

**Acceptance:** an isolated consumer authors a small legally reusable second system, installs it under a new ID using public SDK/API documentation, creates a schema-valid character, rejects invalid state, opens a usable sheet, performs a roll and permission-checked resource action, and retains the result across reload/archive recovery and version upgrade/rollback. No engine source edit should be needed to add that system. This finite demonstration is sufficient to test the extension promise; reproducing Roll20's catalog is not required.
